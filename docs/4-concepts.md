# 第一部分：整个项目其实只讲 7 件事

代码里有 100 多个细碎的知识点，但**核心结论只有这 7 条**。
如果时间很紧，读这 7 条 + 跑一遍对应的 lab，就抓住了八成。

每条后面的「→」指向它在哪一章展开、哪个 lab 能亲手验证。

1. **超卖不是「并发」造成的，是「判断和修改之间有窗口」。**
   在 asyncio 里这个窗口就是 `await` 点 —— 只要有 IO 就有它。
   → [3-data-model](3-data-model.md) · [lab1](../labs/lab1_oversell.py)

2. **exactly-once 不存在。** 「处理消息」和「确认消息」分属你的数据库和
   消息队列，无法原子完成。工程答案是 at-least-once + 消费端幂等 =
   **效果上**恰好一次。
   → [3-data-model](3-data-model.md) · [lab2](../labs/lab2_dup_consume.py)

3. **ack 的时机决定投递语义。** 先处理再 ack 是 at-least-once（可能重复）；
   先 ack 再处理就**可能会丢**。丢比重复严重得多 —— 重复可以靠幂等吸收，
   丢了就真没了。
   → [3-data-model](3-data-model.md) · [lab2](../labs/lab2_dup_consume.py)

4. **「写数据库」和「发消息」无法原子。** 所以别真的去「发消息」——
   把消息当**业务数据**写进同一个事务（本地消息表 / Outbox）。
   → [3-data-model](3-data-model.md) · [lab4](../labs/lab4_outbox_twinwrite.py)

5. **Saga 没有隔离性。** 中间的 PENDING 状态对外可见，这是它的固有代价，
   不是实现缺陷。答不出这一点，说明只记住了 Saga 的形状。
   → 下方 §2 · [1-architecture](1-architecture.md)

6. **重试少了退避或抖动，就会从「自愈机制」变成「故障放大器」。**
   下游本来就过载，你还把请求量乘 3 打过去 —— 它永远好不了。
   → [1-architecture §3.6](1-architecture.md) · [lab5](../labs/lab5_retry_storm.py)

7. **锁不是正确性保证。** 它的 TTL 是对「业务耗时」的猜测，而业务耗时会被
   GC 停顿、网络抖动影响 —— **没有上界**。正确性必须来自资源本身
   （fencing token），或者干脆不用锁。
   → 下方 §11 · [lab3](../labs/lab3_lock_fencing.py)

每条都尽量给出**在这个项目里怎么落地**，避免变成纯背诵。

## 1. CAP 与 PACELC

**CAP**：一致性（C）、可用性（A）、分区容忍性（P）三者最多取二。
但严谨地说，**P 不是可选项** —— 网络分区在分布式系统里一定会发生，
所以真正的选择是：分区发生时，你要 C 还是要 A。

**PACELC** 是它的补全：**P**artition 时在 **A** 和 **C** 之间选；
**E**lse（正常运行时）在 **L**atency 和 **C** 之间选。
后者更贴近日常 —— 即使没有故障，强一致也要付出延迟代价。

**在这个项目里**：
- **库存扣减走 CP**。宁可返回"系统繁忙"，也不能超卖。用的是单条原子 UPDATE + 唯一约束。
- **读路径（查订单）走 AP**。允许读到稍旧的数据，换取低延迟。
- 同一个系统里不同数据走不同取舍，这才是常态 —— 不是整个系统选一个。

面试时如果被问"你这个系统是 CP 还是 AP"，正确的回答是
"分路径讨论，并且说清楚哪条路径为什么选哪个"。

## 2. 分布式事务的完整谱系

从强到弱，代价从高到低：

| 方案 | 一致性 | 代价 | 适用 |
|---|---|---|---|
| **2PC**（两阶段提交） | 强一致 | 同步阻塞；协调者单点；提交阶段崩溃会长期占锁 | 同构系统、短事务、参与者少 |
| **TCC**（Try-Confirm-Cancel） | 最终一致 | 业务代码要写三套逻辑（预留/确认/取消），侵入性最强 | 金融、需要精确控制资源 |
| **Saga** | 最终一致 | 无隔离性，中间状态可见；补偿要幂等 | 长流程、多服务编排 |
| **本地消息表** | 最终一致 | 只能保证"本服务发出去了"；需要 relay 和清理策略 | 跨服务事件通知 |
| **最大努力通知** | 最弱 | 不保证到达，靠对账兜底 | 通知类、可容忍丢失 |

**为什么不用 2PC**：它是**同步阻塞**的，参与者在 prepare 之后到 commit 之前
一直占着资源；而且协调者在提交阶段崩溃会导致参与者长期锁定。
跨组织（比如对接支付网关）时根本不可能要求对方实现 prepare/commit。

**这个项目用的是「本地消息表 + Saga」**：
- Saga 负责**同步链路的逆向补偿**（T2 失败→取消单；T3 失败→释放库存）
- 本地消息表负责**异步事件的可靠投递**（订单状态变更 → 下游）

**容易被追问的一点**：Saga 和本地消息表不是替代关系，
它们解决的是两个不同的问题 —— 一个是"怎么撤销已完成的工作"，
一个是"怎么保证事件不丢"。真实系统里经常一起用，本项目就是这样。

## 3. exactly-once 是假象

严格意义上的 exactly-once 需要"处理消息"和"记录已处理"两个动作原子完成。
但这两个动作通常分属**你的数据库**和**消息队列**两个系统，
跨系统原子提交需要 2PC，代价极高，而且主流消息队列都不支持。

所以在工程上：

```
at-least-once（至少一次）+ 消费端幂等 = effectively-once（效果上恰好一次）
```

**"效果上"这个词很重要**：副作用只发生一次，但消息可能被投递多次。

**面试时的正确姿态**：主动指出 exactly-once 做不到，
然后说明你的系统用的是 at-least-once + 幂等。
如果只说"我们做到了 exactly-once"，遇到懂行的面试官会被追问到崩。

**这个项目里**：
- 投递侧是 at-least-once（[relay.py](../services/order/relay.py) 的 XADD 和标记不在同一事务）
- 消费侧幂等（[consumer.py](../services/order/consumer.py) 的 `try_claim_event`）
- 认领和副作用在**同一个事务**里 —— 顺序错了会导致消息被永久跳过
- [lab2](../labs/lab2_dup_consume.py) 能亲手复现这套机制

## 4. 事务隔离级别与 MVCC

Postgres 默认 **Read Committed**。它能防住**脏读**（读到别人未提交的数据），
但防不住：

- **不可重复读**：同一事务里两次读同一行，结果不同
- **幻读**：同一事务里两次范围查询，行数不同
- **丢失更新**：读-改-写之间被别人的写覆盖

**MVCC 的工作原理**（简版）：Postgres 不为读加锁，而是让每行保留多个版本，
事务看到的是"自己开始时的快照"。所以读不阻塞写、写不阻塞读。
代价是旧版本要清理（VACUUM），而且长事务会阻止清理。

**★ 关键认知**：本项目的防超卖**不是靠隔离级别**，而是靠
**单条原子 UPDATE**。即使把隔离级别提到 Serializable 也能防超卖，
但代价是大量序列化失败重试。

「用更强的隔离级别解决问题」通常是错的方向 ——
正确的方向是**让需要原子性的操作变成一条语句**。

## 5. 消息顺序性

**全局有序**非常昂贵：意味着单分区、单消费者，吞吐直接砍到单机上限。

实际做法是**分区内有序**：
- Kafka：同一 partition 内有序，用 key 决定分区（比如用 order_id 做 key）
- Redis Streams：本身就是单流有序，没有分区概念

**消费者组与 rebalance**：
- 一个分区只能被组内一个消费者消费（保证分区内有序）
- 消费者增减会触发 rebalance，期间消费暂停
- Kafka 的 rebalance 是著名的"停顿来源"，新一代协议在改善这一点

**Redis Streams 和 Kafka 的差距**：
Streams 有消费组、XACK、XAUTOCLAIM，足以演示 at-least-once 和幂等消费。
但它**没有真正的分区**，没有跨分区重放，持久化强度也弱（依赖 AOF/RDB）。
轻量场景够用，高吞吐场景必须上 Kafka。

**这个项目里**：只用一条流，天然有序。真正的顺序性问题（跨分区乱序）
只能靠讲解 —— 所以放在这份文档里。

## 6. protobuf 的演进规则

线格式（wire format）里**只存字段编号，不存字段名**。这带来几条铁律：

1. **字段编号永久有效，绝不能复用**
2. 删除字段要 `reserved`，防止后人误用同一个编号
3. 新增字段必须用新编号，且默认值要能兼容旧版本
4. **不要改字段类型**（int32 → string 会让解析彻底错乱）

**为什么这么严**：复用编号会让新旧版本互相解析出**错误的数据，而且不报错**。
线上表现为"偶发的、无法复现的数据错乱"—— 最难查的一类 bug。

详细注释见 [proto/order.proto](../proto/order.proto) 末尾。

**一个实用技巧**：本项目里 `Order.status` 用 `string` 而不是 `enum`。
因为 enum 加值需要双方同时升级 proto，而 string 对未知值天然兼容。
小团队里这是更务实的选择 —— 面试时说出来会显得有实战经验。

## 7. GIL、阻塞驱动与 Python 的并发真相

**GIL**：同一时刻只有一个线程能执行 Python 字节码。
这意味着**多线程不能提升 CPU 密集任务的性能**。

三种并发的适用场景：

| 方式 | 适合 | 不适合 |
|---|---|---|
| 多线程 | 阻塞 IO（但通常有更好的选择） | CPU 密集 |
| 多进程 | CPU 密集 | 共享状态多、启动开销大 |
| asyncio | 高并发 IO | CPU 密集；有同步阻塞调用时会被拖死 |

**★ 最常见的生产事故**：在 asyncio 服务里调用了**同步阻塞**的库
（比如 `psycopg2`、`requests`、`time.sleep`）。
一个这样的调用会卡住**整个事件循环**，所有并发请求一起卡住 ——
而它看起来完全正常，只是"偶尔慢一下"。

**这个项目的防护**：
- 数据库用 `asyncpg`（纯 asyncio）
- HTTP 客户端用 `httpx`（异步模式）
- 重试用 `asyncio.sleep` 而不是 `time.sleep`
- 唯一一处 `time.sleep` 在 [ids.py](../common/ids.py) 的时钟回拨处理里，
  且注明"偏差 ≤5ms 且极少发生，接受这个代价"

**uvloop**：用 libuv 替换默认事件循环，能显著提升吞吐。
但**它在 Windows 上不存在**（没有 wheel），本项目不用。

## 8. 服务发现与 gRPC 负载均衡

本项目为了控制复杂度，地址是写死在配置里的（`127.0.0.1:50051`）。
真实系统里需要一个服务发现机制：

| 方案 | 说明 |
|---|---|
| **DNS + 无头 Service** | K8s 里最常用。把 Service 设成 headless，DNS 返回所有 Pod IP |
| **xDS** | Envoy/Istio 的控制面协议，功能最强也最复杂 |
| **客户端负载均衡** | gRPC 客户端自己解析地址列表并选择后端 |
| **服务端负载均衡** | 前面放一个 L4/L7 代理（Nginx、Envoy） |

**gRPC 的特殊之处**：它是**长连接**。如果前面放一个普通的 L4 代理，
所有请求会固定打到同一个后端 —— 负载均衡完全失效。
所以 gRPC 通常需要 L7 代理（能看懂 HTTP/2 帧），或者用客户端负载均衡。

**这个项目里**：本地用 Consul 注册中心（[common/discovery.py](../common/discovery.py)），
编排时用 K8s 的 Service + DNS（`MM_DISCOVERY=static`）。两种都落地了，
见 [7-deployment.md](7-deployment.md)。

**注册中心式 vs DNS 式**的分工也在这里：Consul 要服务自己注册 + 心跳，
K8s 的 DNS 直接给你一个稳定名字。前者管非 K8s 环境（多机、混合云），
后者管编排环境 —— 在 K8s 里 Consul 通常"失业"，因为 Service 已经做了发现。

## 9. 可观测性三大支柱

| 支柱 | 回答什么问题 | 本项目 |
|---|---|---|
| **日志** Log | 具体发生了什么 | 带 trace_id 的结构化文本日志 |
| **指标** Metric | 系统整体是什么状态 | `/metrics` 的计数器和 p50/p95/p99 |
| **追踪** Trace | 一次请求经过了哪些环节 | 手写的 trace_id 透传 |

**它们的分工**：指标告诉你"出问题了"，追踪告诉你"问题在哪一跳"，
日志告诉你"具体为什么"。

**★ 为什么必须三个都有**：
只有指标 → 知道 QPS 掉了，不知道哪一环；
只有追踪 → 知道慢在 inventory，不知道它为什么慢；
只有日志 → 信息全在，但量太大，你根本不知道从哪开始看。

**p99 为什么比平均值重要**：平均值会被大量快请求稀释。
99% 的请求 10ms、1% 的请求 3 秒 → 平均只有约 40ms，看起来很健康，
但那 1% 的用户正在骂人。**尾延迟才是体验的真实反映。**

还有一个陷阱：**把 10 个服务的 p99 加起来，得不到真实的长尾**。
延迟不是可加的，尾部的组合效应需要实际测量。

**这个项目的一个真实限制**：`/metrics` 是**进程内**的。
三个服务各自一份、多实例各一份。要看到全局必须推到 Prometheus 聚合。
这不是"算不出来"的问题，是"聚合"的问题 —— 见 [metrics.py](../common/metrics.py)。

## 10. 优雅停机与健康检查

**优雅停机的标准流程**：

```
收到信号 → 停止接受新请求 → 等在途请求做完 → 关闭下游连接和资源 → 退出
```

**顺序不能错**。如果先关连接池再停监听，在途请求会在中途拿到
"连接池已关闭"而失败 —— 把本来可以不发生的失败强加给用户。

**readiness 和 liveness 的区别**（这是面试必问，且答错很致命）：

| 探针 | 失败时kubelet做什么 | 用来判断 |
|---|---|---|
| **liveness** | **重启**容器 | 进程是不是死了（死锁、内存泄漏） |
| **readiness** | 从 Service 摘除，**不重启** | 能不能接受流量（依赖没就绪、正在启动） |

**关键点**：liveness 失败会重启进程，所以它**不能**检查下游依赖。
如果 liveness 探针去 ping 数据库，数据库一抖，你所有的 Pod 都会被重启 ——
本来只是数据库问题，现在变成了全站雪崩。

readiness 才可以检查依赖。这个项目里 `/healthz` 检查了 Redis，
它应该被用作 readiness。

**滚动更新不中断服务**依赖的正是 readiness：
新 Pod 就绪之前不接流量，旧 Pod 等新 Pod 就绪后才被摘除。

## 11. Redlock 的争论

Martin Kleppmann（《DDIA》作者）和 antirez（Redis 作者）的著名辩论。

**antirez 的方案**：向 N 个独立的 Redis 实例申请锁，
超过半数成功且总耗时小于锁有效期，才算拿到锁。

**Kleppmann 的反驳**核心是两点：

1. **进程停顿**：GC、虚拟机挂起、网络延迟都会让进程在拿到锁之后停顿很久。
   锁在它停顿期间过期了，它自己不知道，醒来后继续写数据。
2. **时钟漂移**：Redlock 依赖各实例的时钟来判断锁是否过期，
   而时钟可能被 NTP 调整甚至跳变。

**结论不是"Redlock 错了"，而是"用错地方的锁会骗你"**：

- **效率场景**（避免重复劳动，比如重复计算一次昂贵的报表）→ Redlock 够用。
  出错只是白干一次，没有正确性损失。
- **正确性场景**（不能超卖、不能重复扣款）→ 依赖任何基于超时的锁都不安全。
  正确性必须来自资源本身：**fencing token**，或者干脆用
  原子操作/唯一约束把问题消掉。

**这个项目在 [lab3](../labs/lab3_lock_fencing.py) 里亲手复现了这两种场景**，
并且展示了 fencing token 如何在锁失效的情况下仍然保住数据。

**最有价值的一句话**：本项目除 lab3 外**没有任何地方用分布式锁** ——
库存扣减靠原子 SQL，幂等靠唯一约束。能不用锁就不用锁，
因为锁会引入它自己的失效模式。

## 12. Temporal：如果用框架会怎么做

本项目刻意手写了 Saga、Outbox、relay、重试、幂等 ——
因为要看的就是这些机制本身。

**Temporal 能一举覆盖其中四个**：
它把"工作流"作为一等公民，自动持久化每一步的状态，
所以进程崩溃后能从断点恢复。于是：

| 本项目手写 | Temporal 对应 |
|---|---|
| Saga 编排 + 补偿 | Workflow 里的 try/catch + 补偿调用 |
| Outbox + relay | 不需要。工作流状态本身就是持久化的 |
| 重试 + 退避 | Activity 的 RetryPolicy，声明式配置 |
| 幂等 | 大部分场景不需要。Activity 默认 at-least-once + 工作流状态去重 |
| 超时预算 | Activity 的 StartToCloseTimeout |

**为什么本项目不用它**：
- 它会把上面那些机制**藏起来**，而面试考的正是这些机制
- 它需要额外部署一个 Temporal Server + 它自己的数据库
- 2-3 天不够

**但你应该知道它**：面试里被问"你们的重试和补偿怎么做的"，
答完自己的实现后补一句"如果流程更复杂，我会考虑 Temporal 这类
持久化工作流引擎，因为它把状态恢复和重试都变成声明式的"——
这比只会手写加分。

**要避开的坑**：`Nameko` 常被推荐为"Python 微服务框架"，
但它基于 `eventlet`（不是 asyncio 原生），而 eventlet 在 2026 年已实质废弃，
且与 asyncio 冲突。**不要用**。

---

## 13. 最后：什么是最危险的失败

这个项目在开发过程中真实踩到的三个"静默失效"，
它们的共同点是：**看起来有保护，实际上没有**。

| 现象 | 原因 | 教训 |
|---|---|---|
| 本该报错的请求**静默成功** | `grpc.aio` 的 `context.abort` 是协程，没 await 就只是创建了个没人要的协程对象 | 异步 API 忘记 await 不会报错，只会静默失效 |
| trace_id 有时有有时没有 | 在 gRPC 的 `intercept_service` 里 set contextvar，但真正的 handler 跑在另一个作用域 | 要想清楚"这段代码在哪个上下文里执行" |
| 加了限流但压测没触发 | 串行 curl 太慢，令牌桶按速率补回来了 | 验证机制时要**真的构造出触发条件** |

**所以最重要的工程习惯是**：每个机制上线前，
**都要能演示它真的在起作用**。

这个项目的 labs 就是为此存在的 ——
`lab1` 证明"不加原子性真的会超卖"，
`lab2` 证明"不幂等真的会重复加分"，
`lab4` 证明"不用 outbox 真的会丢事件"。

**能演示出反例，才算真的理解了机制。**
