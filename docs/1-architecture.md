# 第一部分：微服务系统通常由哪些部分组成

## 先搞清楚：什么是"微服务"

**单体应用**：所有功能在一个进程里。改一个模块要重新部署整个应用。

**微服务**：按业务能力拆成多个**独立部署的进程**，每个进程负责一块业务，
通过**网络调用**互相协作。

拆开之后你支付的代价是：本来一个函数调用就能完成的事，
现在变成了网络请求 —— 会超时、会失败、会乱序、会有多次投递。
**这份文档里的每一个"部分"，本质上都是在对付这个代价。**

> 记住这句话：**微服务的所有复杂度，都来自"把一个函数调用变成了网络调用"。**
> 后面看到超时、重试、幂等、消息队列、链路追踪，全都源于此。

---

## 一个微服务系统通常有这 8 个部分

| # | 部分 | 解决什么问题 | 不做会怎样 |
|---|---|---|---|
| 1 | 网关 | 外部流量统一入口 | 每个服务都要自己处理鉴权、限流 |
| 2 | 业务服务 | 装业务逻辑 | —— |
| 3 | 服务间通信 | 服务怎么互相调用 | —— |
| 4 | 数据存储 | 状态放哪 | —— |
| 5 | 服务发现与配置 | 怎么找到对方、配置怎么下发 | 换个 IP 就要改代码重新部署 |
| 6 | 可观测性 | 出问题怎么查 | 只能靠猜 |
| 7 | 弹性机制 | 依赖挂了怎么办 | 一个下游故障拖垮全站 |
| 8 | 部署与编排 | 怎么跑起来、怎么扩容 | —— |

下面逐个展开。

---

### 1. 网关（Gateway）

**它解决什么问题**：外部客户端不应该直接调用你的每个微服务。

如果没有网关，客户端要记住 3 个服务的地址，而且每个服务都得自己实现
鉴权、限流、日志。加一个服务就要改一次客户端。

**网关做这些事**（都是"横切关注点"——和具体业务无关，每个服务都需要）：
- **鉴权**：验证这个请求合不合法，一次验完，内部服务就信任它
- **限流**：某个用户狂刷，在入口就拦住，别让流量打到后面
- **协议转换**：对外 HTTP（通用），对内 gRPC（高效）
- **路由**：`/orders` 转发给 order 服务，`/users` 转发给 user 服务
- **链路追踪的起点**：给每个进来的请求分配一个 ID

**关键原则**：网关只做横切关注点，**不做业务判断**。
一旦开始做业务，业务逻辑就分散在网关和下游两处，日后必然不一致。

**在本项目里**：`services/gateway/`，一个 FastAPI 应用，监听 8000 端口。
它只做四件事：限流、生成 trace_id、转发给 order 服务、把 gRPC 错误码翻译成 HTTP 状态码。

---

### 2. 业务服务（Services）

**它解决什么问题**：把业务逻辑按能力拆开，各自独立部署、独立扩容。

**拆分原则**（重要的不是拆几个，而是按什么拆）：
- 按**业务能力**拆，不是按技术层拆（不是"controller 服务"、"dao 服务"）
- 每个服务应该能**独立修改和部署**，不用协调别人
- 服务之间的调用应该是**粗粒度**的。如果一个请求要调 10 个服务，
  说明拆得太细了

**在本项目里**：两个业务服务
- `services/order/` —— 订单：下单、幂等、状态机、事件投递
- `services/inventory/` —— 库存：扣减、预留、补偿

为什么只有两个？因为业务本身很简单（下单扣库存）。
**服务数量不是重点，它们之间的协作方式才是。**

---

### 3. 服务间通信（Inter-service Communication）

**它解决什么问题**：拆开之后，服务之间怎么说话。

分两大类，**这两种本项目都用了**：

| 方式 | 特点 | 适合 |
|---|---|---|
| **同步 RPC**（gRPC / HTTP） | 调用方**等**结果，有返回值 | 需要立刻知道结果的：扣库存 |
| **异步消息**（MQ / 事件） | 发出去就不管，接收方稍后处理 | 不需要立刻知道结果的：加积分、发通知 |

**怎么选**：
- 用户正等着看结果 → 同步
- "这件事发生了，相关方自己处理" → 异步

**在本项目里**：
- 同步：gateway → order → inventory，全部用 **gRPC**
- 异步：order 发出"订单已确认"事件 → 消费者加积分，用 **Redis Streams**

---

### 4. 数据存储（Data Stores）

**它解决什么问题**：状态放哪。

**微服务的一条重要原则：每个服务有自己的数据，不共享数据库。**

为什么？如果两个服务直接读同一张表，那它们的改动就耦合了 ——
A 改字段，B 就挂了。这叫"分布式单体"，拆了个寂寞。

**代价**：跨服务的数据一致性变得很难 —— 这就是为什么需要 Saga、
本地消息表这些模式（见 [4-concepts.md](4-concepts.md)）。

**数据存储一般分两层**：
- **数据库**：真相之源，持久化，ACID
- **缓存**：加速读取，可丢失，通常是 Redis

**在本项目里**（真实项目里会更严格，这里做了简化）：
- Postgres：订单、库存、outbox、幂等表
- Redis：限流令牌桶、分布式锁、消息流

> 严格来说本项目三个服务**共用一个 Postgres**（这是简化）。
> 真实项目里订单库和库存库应该是独立的，甚至可以用不同类型的数据库。
> 但共用库不影响学习重点 —— 我们**没有任何跨服务的事务**，
> 服务之间只通过 gRPC 和消息通信，这和分库是一致的。

---

### 5. 服务发现与配置（Discovery & Config）

**它解决什么问题**：order 服务怎么知道 inventory 服务在哪？

开发时地址是固定的 `127.0.0.1:50052`。但生产环境里：
- 服务会动态扩缩容，实例数量和 IP 一直在变
- 实例会挂掉重启，IP 会变
- 灰度发布时同时存在两个版本

**解决方案**（常见三种）：
- **服务注册中心**：etcd / Consul / ZooKeeper。服务启动时注册自己，调用方查表
- **DNS**：K8s 里最常用。每个 Service 有一个 DNS 名，解析出所有 Pod IP
- **服务网格**：Istio / Envoy，把流量管理下沉到基础设施层

**配置管理**关心的是另一件事：环境变量、密码、限流阈值从哪来。
12-Factor App 的原则是"配置存于环境"，而不是写死在代码里。

**在本项目里**：**本地开发用 Consul 注册中心**（`common/discovery.py`）——
服务启动时注册自己、定期心跳，调用方通过 `resolve()` 查到地址；
K8s 编排下切换成 **DNS 式发现**（`MM_DISCOVERY=static` + Service 名）。
两种方式都落地了，见 [7-deployment.md](7-deployment.md) 第一部分。

---

### 6. 可观测性（Observability）

**它解决什么问题**：系统是分布的，出问题时你没法登录一台机器看日志。

**三大支柱**：

| 支柱 | 回答什么问题 | 本项目 |
|---|---|---|
| **日志** Log | 具体发生了什么 | 带 trace_id 的结构化文本日志 |
| **指标** Metric | 系统整体什么状态 | `/metrics` 的计数器和 p50/p95/p99 |
| **追踪** Trace | 一次请求经过了哪些环节 | 手写的 trace_id 跨进程传递 |

**为什么必须三个都有**：
- 只有指标 → 知道 QPS 掉了，不知道哪一环
- 只有追踪 → 知道慢在 inventory，不知道它为什么慢
- 只有日志 → 信息全在，但量太大，不知道从哪看起

**核心机制是 trace_id**：给每个进来的请求分配一个 ID，
之后每次跨服务调用都带上它，每个服务的日志里都打印它。
于是你可以用一条命令把散落在三个进程日志里的行串成一次完整的调用。

**在本项目里**：`common/trace.py`（追踪）、`common/metrics.py`（指标）、
`common/logging.py`（日志）。

---

### 7. 弹性机制（Resilience）

**它解决什么问题**：网络调用会失败。失败了怎么办？

这一部分包含好几个机制，**它们解决的问题各不相同**：

| 机制 | 解决什么 | 一句话 |
|---|---|---|
| **超时（Timeout）** | 不能无限等 | 给每次调用设一个上限 |
| **重试（Retry）** | 瞬时故障 | 抖动 + 退避地重来 |
| **熔断（Circuit Breaker）** | 下游持续故障 | 连续失败就快速拒绝，别再拖累自己 |
| **限流（Rate Limit）** | 流量过大 | 主动拒绝一部分，保护自己 |
| **降级（Fallback）** | 熔断之后 | 返回一个次优但可用的结果 |
| **幂等（Idempotency）** | 重试导致重复执行 | 同一请求执行多次 = 一次 |

**这几个机制之间的顺序很重要**，比如熔断必须包在重试外面
（否则熔断拦不住重试产生的流量放大）。

**在本项目里**：`common/retry.py`、`common/breaker.py`、
`common/ratelimit.py`、`common/errors.py`（判断该不该重试）。

---

### 8. 部署与编排（Deployment）

**它解决什么问题**：这么多进程，怎么跑起来、怎么扩容、怎么发布新版本。

- **容器化**：Docker，把应用和依赖打包，解决"我这能跑"的问题
- **编排**：K8s，负责调度、扩缩容、健康检查、滚动发布
- **健康检查**：readiness（能不能接流量）/ liveness（要不要重启）

**在本项目里**：**补上了**。有 `deploy/Dockerfile` 打镜像、
`deploy/docker-compose.yml` 全栈容器化、`deploy/k8s/` 下整套 K8s 清单
（中间件走外部）。本机开发时业务服务仍跑宿主机（方便读日志下断点），
要上 K8s 时切过去即可。详见 [7-deployment.md](7-deployment.md)。

## 三个服务各自负责什么

| 服务 | 端口 | 协议 | 职责 | 代码位置 |
|---|---|---|---|---|
| gateway | 8000 | HTTP | 限流、trace 起点、协议转换 | [services/gateway/](../services/gateway/) |
| order | 50051 | gRPC | 下单、幂等、Saga、事件投递 | [services/order/](../services/order/) |
| inventory | 50052 | gRPC | 扣库存、预留、补偿 | [services/inventory/](../services/inventory/) |

**每个服务内部都是同样的四层**，依赖方向单向：

```
main.py       进程入口：起服务、装拦截器、优雅停机
   ↓
grpc_api.py   传输层：解析请求 → 调 service → 映射错误（薄，无业务逻辑）
   ↓
service.py    业务层：编排、事务边界、幂等（不 import grpc）
   ↓
repo.py       数据层：SQL（不管事务边界，由 service 决定）
```

**为什么要这样分层**：`service.py` 不 import grpc，意味着换掉传输协议
（gRPC → HTTP → 消息消费者）时业务逻辑一行都不用改。
这也是业务逻辑能被单元测试的前提。

## 为什么这样拆

**为什么 order 和 inventory 要拆开？**
不是"因为微服务很酷"。是因为**库存的写入和订单的写入有本质不同的并发特征**：
库存是热点（同一件商品所有人抢），需要原子扣减；
订单是每个用户自己的，几乎不冲突。
拆开后可以分别优化、分别扩容。

**为什么 gateway 要单独一层？**
限流和协议转换是所有入口都需要的能力。放在网关，order 和 inventory
就不用各写一遍。而且对外只暴露一个地址，内部服务可以随便重构。

# 第三部分：服务之间怎么调用

用户最关心的部分。分 6 个小问题讲。

## 3.1 用什么协议？

| 边界 | 协议 | 为什么 |
|---|---|---|
| 客户端 → gateway | **HTTP/JSON** | 通用，任何客户端都能调，方便调试 |
| gateway → order | **gRPC** | 内部通信，需要高性能 + 强类型契约 |
| order → inventory | **gRPC** | 同上 |
| order → 消费者 | **Redis Streams** | 异步，发送方不等结果 |

**为什么内部用 gRPC 而不是 HTTP/JSON**：
- **二进制编码**：protobuf 比 JSON 小得多，序列化更快
- **强类型契约**：`.proto` 文件明确定义了字段和类型，改错了编译期就报错
- **HTTP/2**：一条连接上多路复用，没有队头阻塞
- **原生支持 deadline 传递**：这是本项目重点演示的机制

**为什么外部用 HTTP**：浏览器和 curl 不会说 gRPC。

## 3.2 服务地址从哪来？

服务地址**不再写死**，而是动态解析（[common/discovery.py](../common/discovery.py)）：

- 本机开发：服务启动时向 **Consul** 注册自己，调用方 `resolve()` 查到地址。
- K8s 编排：`MM_DISCOVERY=static`，直接用 Service 的 DNS 名（`order:50051`）。

```python
order_addr     = "127.0.0.1:50051"   # 这是"兜底地址"：Consul 解析失败时用它
inventory_addr = "127.0.0.1:50052"
```

可以用环境变量覆盖（`MM_ORDER_ADDR=...`）。

两个要点：

- **注册中心是基础设施，它挂不该拖垮业务** —— 所以解析失败会回落这个静态地址，
  整套系统退化回"写死地址"也能跑。
- **"静态还是动态"才是本质区别**。写死地址本身没错（所有服务都在本机时它完全正确），
  错的是在地址会变的环境里仍然假设它不变。见 [7-deployment.md](7-deployment.md)。

## 3.3 一次调用的完整经过（时序）

以"下单"为例，看一个请求怎么在三个进程间流转：

```
 客户端          gateway         order            inventory      Postgres/Redis
   │                │              │                  │                │
   │ POST /orders   │              │                  │                │
   ├───────────────>│              │                  │                │
   │                │              │                  │                │
   │                │ 1. 限流检查（Redis 令牌桶）────────────────────────>│
   │                │ 2. 生成 trace_id（链路起点）                      │
   │                │              │                  │                │
   │                │ 3. gRPC CreateOrder(deadline=3000ms)             │
   │                ├─────────────>│                  │                │
   │                │              │                  │                │
   │                │              │ 4. 幂等检查 (查询api_idempotency表)>│
   │                │              │ 5. T1: 事务{INSERT orders}        │
   │                │              │         {INSERT outbox} ────────>│
   │                │              │                  │                │
   │                │              │ 6. gRPC Reserve(deadline=1000ms)  │
   │                │              ├─────────────────>│                │
   │                │              │                  │ 7. 原子扣减 ──>│
   │                │              │                  │    UPDATE ...  │
   │                │              │<─────────────────┤    WHERE stock │
   │                │              │   ok, remaining  │      >= $1     │
   │                │              │                  │                │
   │                │              │ 8. T3: 支付（本地函数，可能失败）  │
   │                │              │ 9. T2: 事务{UPDATE orders=CANCELLED}│
   │                │              │         {INSERT outbox} ────────>│
   │                │<─────────────┤                  │                │
   │<───────────────┤ 201 Created  │                  │                │
   │  x-trace-id    │              │                  │                │
   │                │              │                  │                │
   │                │         ┌────┴──────────────────────────────────┐
   │                │         │ 后台任务（不在这条链路上）              │
   │                │         │ relay:  outbox → Redis Stream          │
   │                │         │ consumer: Stream → 加积分              │
   │                │         └───────────────────────────────────────┘
```

**几个关键点**：

- **步骤 1 限流在最前面** —— 被限流的请求不该消耗任何下游资源
- **步骤 5 的两条 INSERT 在同一个事务里** —— 这是本地消息表模式的核心
- **步骤 6 的 deadline 是 1000ms，而 gateway 给的是 3000ms** —— 逐跳收紧
- **步骤 9 之后还有后台任务** —— 事件投递是异步的，不阻塞用户请求

## 3.4 trace_id 怎么跟着走？

这是"分布式追踪"的全部机制，**没有任何魔法**：

```
1. gateway 收到请求，生成 trace_id = "abc123"
2. gateway 发 gRPC 请求时，把 trace_id 放进 metadata（就是请求头）
3. order 的拦截器收到请求，从 metadata 里取出 trace_id，
   存进 contextvars（当前协程的"上下文变量"）
4. order 的日志自动带上这个 trace_id
5. order 调 inventory 时，客户端拦截器再把 trace_id 放进 metadata
6. inventory 同样取出、存进 contextvars、日志带上
```

结果：三个进程的日志里都有同一个 `abc123`，你可以一条命令串起来：

```powershell
Select-String -Path logs\*.log -Pattern "abc123" -SimpleMatch
```

实现见 [common/trace.py](../common/trace.py)（约 100 行，注释很详细）。

**为什么用 contextvars 而不是全局变量**：一个进程同时处理上千个请求，
全局变量会被互相覆盖。contextvars 是按协程隔离的。

## 3.5 超时怎么传递？

这是 gRPC 比 HTTP 强的地方，也是面试常问的点。

**核心概念：deadline 是一个绝对时间点，不是"等多久"。**

```
gateway 说：这次调用 3000ms 内必须结束
   ↓（deadline 随请求传下去，每一跳自动扣减已消耗的时间）
order 收到时，发现只剩 2998ms
   ↓ order 决定给下游最多 1000ms（自己留 2 秒处理别的）
inventory 收到时，看到自己的 deadline 是 1000ms
```

**为什么子调用的超时必须小于自己的剩余时间**：
如果 order 把全部剩余预算都给了 inventory，那么 inventory 超时返回时，
order 自己也没时间了 —— 它连"把订单标记为失败"都来不及做。
所以必须留一点缓冲给收尾工作。

实现见 [common/clients.py:child_timeout()](../common/clients.py)。

> 顺带回答一个常见问题：**deadline 和 timeout 有什么区别？**
> `timeout` 是"我这次愿意等 3 秒"，是一个相对时长。
> `deadline` 是一个绝对时间点，会随请求传播并自动扣减。
> 所以链路末端看到的剩余时间，天然就是"整条链路还剩多少"。

## 3.6 调用失败了怎么办？

按失败类型分三种处理，**这个分类是重点**：

| 失败类型 | 例子 | 处理方式 |
|---|---|---|
| **业务失败** | 库存不足 | **不重试**。重试一万次还是没货。返回明确结果 |
| **系统瞬时故障** | 网络抖动、下游重启 | **重试**（带退避和抖动） |
| **系统持续故障** | 下游挂了 | **熔断**，快速失败，别再拖累自己 |

**怎么区分？看 gRPC 状态码**：

| 状态码 | 可重试？ | 为什么 |
|---|---|---|
| `UNAVAILABLE` | ✅ | 对端挂了，可能是瞬时的 |
| `DEADLINE_EXCEEDED` | ✅ | 超时，可能只是慢 |
| `FAILED_PRECONDITION` | ❌ | 前置条件不满足（如库存不足） |
| `INVALID_ARGUMENT` | ❌ | 参数错了，重试还是错 |
| `NOT_FOUND` | ❌ | 资源不存在 |

判断逻辑见 [common/errors.py](../common/errors.py) —— 注意它用的是
**白名单**（只有明确知道可重试的才重试），因为错误地重试比不重试更危险。

**另一个关键点：重试会引入重复执行**。
一次调用可能实际执行了两次（第一次成功了但响应丢了，你重试了第二次）。
所以**所有会被重试的操作都必须幂等** —— 这就是为什么本项目到处都是
幂等表和唯一约束。详见 [2-api.md](2-api.md) 和 [3-data-model.md](3-data-model.md)。
